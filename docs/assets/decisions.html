rslm Overview Architecture Features Decisions Roadmap

Design Decisions

Key architectural choices, tradeoffs considered, and rationale.

D-001 Rhai over Python for the scripting layer spec 2026-04-23

The Zhang & Khattab paper uses Python as the REPL environment. rslm uses Rhai — an embedded Rust scripting language — instead.

Why: No subprocess, no Python runtime dependency. Rhai runs in-process, shares memory with the host, and enforces a bounded operation count (set_max_operations). Scripts are sandboxed without any OS-level isolation. The API surface is identical to what the paper describes — the model writes short imperative scripts to query context.

Tradeoff: The model must write valid Rhai rather than Python. GPT-4o and Claude produce correct Rhai with the system prompt as guide; the self-correction loop handles occasional syntax errors. Rhai lacks Python's data manipulation ecosystem (no json, no re stdlib), but rslm provides the primitives the model actually needs (ctx_grep, ctx_slice, etc.) as registered functions.

D-002 Context never sent to the LLM directly spec 2026-04-23

Raw context is stored in the Rhai engine's state. The model only sees what it explicitly extracts via registered functions. The full text never appears in a message.

Why: This is the core RLM invariant. It forces the model to reason about what it needs rather than pattern-matching over a wall of text. It also bounds token usage — large contexts don't inflate every API call.

Tradeoff: The model must write multiple scripts to build up enough information for an answer. For small contexts this is slower and more expensive than a direct call. rslm is intended for contexts that exceed the model's window, not as a general-purpose wrapper.

D-003 Blocking recursion via spawn_blocking + new current-thread runtime spec 2026-04-23

rlm_call(q, ctx) is a synchronous Rhai function. The child Rlm::run is async. The bridge: tokio::runtime::Builder::new_current_thread().block_on(...) inside a spawn_blocking call.

Why: Rhai functions cannot be async. The Rhai engine is not Send in its default configuration — rslm uses features = ["sync"] to enable Send + Sync engine closures. Creating a new single-threaded runtime per child is the simplest correct bridge given these constraints.

Tradeoff: Sequential children only. Parallel rlm_call dispatch (multiple concurrent sub-queries) is not supported. This is listed as a non-goal in the spec and deferred to future work.

Test implication: Tests that exercise rlm_call end-to-end must be #[ignore]d or use spawn_blocking — calling block_on inside an existing Tokio test runtime panics.

D-004 Fresh Scope::new() per script execution — no persistent state spec 2026-04-23

Each Rhai script runs in a new empty scope. Variables defined in one script are not visible in the next.

Why: Simplicity and reproducibility. The model must be explicit about what it carries forward — it either calls print_cell (which appends to cell output, which becomes message history) or it re-extracts from context. This matches the paper's design.

Tradeoff: The model cannot accumulate a running data structure across cells. For tasks requiring multi-step aggregation it must carry state through print_cell output or inline JSON strings passed between rlm_call invocations. This is workable but slightly awkward for complex aggregations.

D-005 Trait-based provider abstraction, env-var selected at runtime spec 2026-04-23

LlmProvider: Send + Sync with a single async fn complete method. Two impls: OpenAiProvider and AnthropicProvider. Selected via RSLM_PROVIDER + RSLM_MODEL or CLI flags.

Why: Keeps rslm-core and rslm-cli independent of specific API clients. Adding a new provider (Ollama, Gemini) requires only a new impl file in rslm-providers and a match arm in the CLI. The core loop is unchanged.

Tradeoff: rlm-rs hardcodes a root/sub-agent model tier (Opus + Haiku). rslm uses a single provider throughout the recursion tree — the same model handles root and child instances. Tiered models (expensive root, cheap children) would require passing a separate child provider, which is possible but not yet implemented.

D-006 Optional ChunkStore — zero behavior change when absent #4 #5

build_engine() accepts store: Option<Arc<ChunkStore>>. When None, no chunk Rhai functions are registered and no system prompt addendum is injected. Existing callers compile and behave identically.

Why: rslm's primary value is the RLM loop, not chunking. Chunking is an additive enhancement for large persistent corpora. Making it optional preserves the simple fast path for users who just want to run a query against inline context.

Tradeoff: The Rlm struct grows fields (store, embedder, doc_id). A builder pattern or separate constructor is preferred over breaking the existing Rlm::new() signature.

D-007 Inline BM25 — no external scorer crate #6

BM25 is implemented from scratch in ~120 lines in bm25.rs with no external dependency. Parameters: k1=1.5, b=0.75 (standard BM25 defaults).

Why: The BM25 algorithm is well-defined, short, and has no external API surface to track. Adding a crate dependency for <150 lines of math is not warranted. It also avoids transitive dependency conflicts in the workspace.

Tradeoff: No stemming, no stopword removal, no language-aware tokenization. Tokenization is lowercase + split on non-alphanumeric. Sufficient for the use case (keyword search over text chunks). If richer NLP is needed later, swapping in a crate-backed impl is straightforward given the Bm25Index API boundary.

D-008 Per-chunk idempotent ingest via INSERT OR REPLACE ON (doc_id, idx) #5

The chunks table has UNIQUE(doc_id, idx). Ingest uses INSERT OR REPLACE. Re-running ingest after a partial failure or crash is safe — existing chunks are overwritten, missing ones are inserted.

Why: Whole-doc skip ("skip if doc_id exists") would leave partially-ingested documents permanently broken after a crash mid-ingest. Per-chunk upsert is strictly safer at negligible extra cost.

D-009 RRF constant k=60 (standard default) #5

Reciprocal Rank Fusion: score(d) = Σ_r 1/(60 + rank_r(d)). The constant 60 is the value from the original RRF paper (Cormack et al., 2009) and the most common default in production search systems.

Why: k=60 gives good empirical performance across a wide range of corpora. Making it configurable adds API complexity for marginal gain at this stage. It can be exposed as a parameter if tuning becomes necessary.

D-010 HNSW unit tests use 128-dim vectors, not 4-dim #9

The HNSW unit test generates ~20 random 128-dimensional unit vectors rather than 4-dim.

Why: HNSW is an approximate nearest-neighbor algorithm. Its graph construction and traversal heuristics behave differently at very low dimensions — 4-dim spaces are nearly exhaustively searchable and don't exercise the approximation behavior the index is designed for. 128-dim is a realistic minimum for embedding-like vectors and produces meaningful ANN test coverage.
